# Пререндеринг контента в обычной сборке

## Что сейчас на самом деле
- `seoPlugin` уже подключён в `vite.config.ts` и срабатывает при обычном `vite build` (то есть и при публикации Lovable). Он создаёт отдельный HTML для каждого маршрута из `seo-routes.ts`, но кладёт туда только мета-теги.
- Пустой `<div id="root"></div>` заполняется только для статей блога (текст статьи + `<h1>`) и для страниц-редиректов. Остальные ~160 страниц аудитор видит пустыми: 0 слов, нет h1.
- Поэтому новый отдельный шаг публикации не нужен: достаточно, чтобы тот же плагин вставлял настоящую разметку страницы.

## Механизм: SSG через React SSR внутри `closeBundle`
1. Новый серверный вход `src/entry-server.tsx`: `render(url)` отдаёт `renderToString(<HelmetProvider><StaticRouter location={url}><AppRoutes/></StaticRouter></HelmetProvider>)`.
2. Из `App.tsx` выносим дерево маршрутов в `AppRoutes` (без `BrowserRouter`) — клиент и сервер используют одно и то же. Клиентская часть не меняется.
3. В `closeBundle` плагин делает программную SSR-сборку Vite (`build({ build: { ssr: "src/entry-server.tsx", outDir: "dist-ssr" } })`), импортирует результат и для каждого маршрута вставляет HTML в `#root`. Мета-теги по-прежнему берутся из `seo-routes.ts` (как сейчас) — один источник, без дублей.
4. Клиент оставляем на `createRoot` (не `hydrateRoot`): React просто заменяет готовую разметку. Так нет риска ошибок «hydration mismatch», а боты получают текст. Позже можно перейти на гидрацию.
5. Ленивые страницы: на сервере `lazyWithRetry` заменяется на синхронный импорт (через флаг `import.meta.env.SSR`), иначе `renderToString` отдаст пустой Suspense. Ленивые секции главной (`LazySection`) на сервере рендерят содержимое сразу.
6. Блог: статьи берутся из уже сгенерированного при `prebuild` манифеста/`dbBlogPosts.generated.ts` — в сборке Supabase не опрашивается. Текущая вставка тела статей остаётся как запасной вариант, если SSR страницы упадёт.
7. Защита: если рендер конкретного маршрута падает, плагин пишет предупреждение и оставляет текущий HTML с мета-тегами — публикация не ломается.

## Проверка
- `verify-prerender-seo.mjs` дополняем: на каждой странице ровно один `<h1>`, в `#root` не меньше ~150 слов, нет дублей title/canonical.
- `seo:check` вызывается из плагина в конце `closeBundle`, поэтому выполняется при каждой публикации; в первой версии — только предупреждения, без остановки сборки.
- Дополнительно — `test:geo` и выборочная проверка через curl без JS: /, /about, /anxiety, /burnout, /psiholog-dlya-it, /tools/tests, статья блога.

## Затрагиваемые файлы
- новые: `src/entry-server.tsx`, `src/AppRoutes.tsx`
- `src/App.tsx` (вынос маршрутов), `src/lib/lazyWithRetry.ts`, `src/components/LazySection.tsx`
- `vite-plugin-seo.ts` (SSR-сборка и вставка разметки), `scripts/verify-prerender-seo.mjs`
- точечно — компоненты, которые обращаются к `window`/`localStorage`/`document` прямо при рендере (Navbar, ExitIntentPopup, инструменты, тесты): перенос в `useEffect`

## Риски
- Код, трогающий браузерные объекты при рендере, уронит SSR конкретной страницы — закрыто пунктом 7, исправляем по списку предупреждений.
- Анимации framer-motion с `initial={{opacity:0}}` попадут в HTML невидимыми: текст для ботов есть, но Google видит его как скрытый до JS. Для SSR-вывода отключим начальную прозрачность (`MotionConfig` / `initial={false}` на сервере).
- Время сборки вырастет примерно на 20–60 секунд (≈190 страниц).
- Краткая «вспышка» при загрузке: готовая разметка заменяется React. Если заметна — следующий шаг `hydrateRoot`.
- Admin-страницы, `/thank-you`, noindex — не пререндерим содержимое.

## Технические детали
SSR-сборка: `vite.build` с `ssr`, `ssr.noExternal` для пакетов с CSS-импортами (framer-motion, radix). Шаблон вставки — замена `<div id="root"></div>` на `<div id="root">${html}</div>`. Helmet-контекст на сервере не используем для head (мета из seo-routes), только чтобы компоненты не падали. Решение фиксируется в `AGENTS.md`.
